    Plan and manage costs for Microsoft Foundry

    Foundry is made up of several optional Azure services, so there's no single line item in the Azure pricing calculator. This guide shows how to estimate costs for the services in your architecture, validate the estimates, and reconcile them before rolling out to production.

    The cost lifecycle in the guide

    Select a step
    1 · Estimate

    Estimate costs for each of the services in your architecture, since Foundry has no single line item in the Azure pricing calculator.

    2 · Validate

    Validate those estimates with a small test workload.

    3 · Reconcile

    Reconcile the estimates against actual meter-level charges in Microsoft Cost Management before rolling out to production.

    4 · Monitor

    Once you're running, monitor spend in the Foundry portal, where you can see estimated costs for agents and model deployments by project and date range.

    5 · Allocate and control

    In Cost Management in the Azure portal, break down costs by resource and meter, allocate shared spend back to teams with project-level chargeback (preview), set up budgets and alerts, and export cost data for analysis in tools like Excel or Power BI.

    Attribute and cap model spend

    Azure AI Gateway turns token usage into estimated USD cost and emits it as OpenTelemetry metrics you can send to Application Insights or your own dashboards.

    Token usage
    Estimated USD cost
    OpenTelemetry metrics
    Application Insights or your dashboards

    Attribute

    Give each application its own API key, or add validated Microsoft Entra claims as metric dimensions, to see exactly which applications, callers, and cost centers are driving model spend.

    Cap

    Cost-limit policies give each API key or Entra identity its own estimated USD allowance that renews on a set period, such as weekly or monthly, with overrides to raise or lower the limit for specific callers.

    These are estimates based on a Microsoft-maintained pricing catalog, not billing records. The docs also cover how costs are calculated and how to spot models with missing prices.

    Lower the cost of each request

    Model router is a model you deploy like any other, but it looks at each prompt and sends it to the most suitable underlying model, so simple requests don't pay frontier-model prices.

    Model router: choose a routing mode

    Lower qualityHigher quality

    Balanced (the default) picks the cheapest model within a narrow quality range of the best one. Here that routes to model C.

    • Cost widens that range to save more. Quality always picks the highest-rated model.
    • The usable context window is limited by the smallest underlying model, so use a model subset if you need longer contexts, and compare the router against your current setup before switching.

    Prompt caching: order matters

    Illustrative prompt
    1. Date stampChanges every call
    2. System instructionsStable
    3. Tool definitionsStable
    4. Fraud policy textStable
    5. Case detailsChanges every call

    No cached prefix. The first block changes on every call, so the cache never gets a hit. This is the version 2 problem from the demo.

    • Prompt caching reuses identical prompt prefixes, so keep stable content such as system instructions and tool definitions at the top and put content that changes at the bottom.
    • Cache reads are discounted on standard deployments, but GPT-5.6 and later models can also charge for cache writes, so a prefix that keeps changing costs more.

    Global batch

    For work that doesn't need an immediate answer, global batch processes large jobs from a single file with a 24-hour target turnaround at 50% less than global standard pricing. It uses its own quota, so live traffic isn't affected.

    Commit to capacity with PTUs, reservations, and prepurchase

    Provisioned throughput units (PTUs) reserve dedicated model capacity for a deployment and are billed per PTU per hour whether or not you send traffic. Pick the workload below to see which option the docs point to.

    Which option fits the workload?

    Provisioned throughput (PTUs)
    • Dedicated capacity, billed per PTU per hour whether or not you send traffic. That pays off for predictable, high-volume, latency-sensitive workloads.
    • Use the sizing and billing guides to work out how many PTUs a workload needs.
    • Spillover can send requests that overflow a busy provisioned deployment to a matching standard deployment.
    • To lower the hourly PTU rate, buy a Foundry Provisioned Throughput Reservation for a one-month or one-year term.
    Standard pay-per-token deployments
    • Standard pay-per-token deployments remain the better fit for development and unpredictable traffic.
    • PTUs bill every hour whether or not you send traffic, so they suit predictable, high-volume, latency-sensitive workloads instead.
    Global batch
    • Processes large jobs from a single file with a 24-hour target turnaround.
    • Costs 50% less than global standard pricing.
    • Uses its own quota, so live traffic isn't affected.
    Microsoft Agent Prepurchase Plan
    • Sells discounted Agent commit units for a one-year term.
    • Pays down eligible usage across Foundry, Copilot Studio, Fabric, and GitHub.
    • Its discount doesn't combine with other discounts you already have.

    Good to know

    PTU quota is granted per subscription, region, and deployment type, not per model.
    Reservations are bought separately for Global, Data Zone, and Regional deployments.
    Reservations don't guarantee capacity, so create your deployments first.
    Deleting a deployment doesn't cancel its reservation.
